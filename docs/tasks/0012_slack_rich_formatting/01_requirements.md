## 1. 背景と目的

### 1.1 背景

[0006_slack_notification](../0006_slack_notification/01_requirements.md) で Slack Webhook 通知の送信・チャンネル振り分け・サニタイズ・マスキングという基盤を実装した。同タスクは「通知メッセージの詳細フォーマット（attachment の色・絵文字・Run ID 等のリッチ表現）」を明示的にスコープ外とし（同ドキュメント 2 節・5 節）、姉妹プロジェクト `go-safe-cmd-runner`（`internal/logging/slack_handler.go`）の attachment ベースのリッチ表現を将来の参考実装として位置づけていた。

本タスクはその「後続検討」を実施し、現在プレーンテキスト（`{"text": "..."}` 形式の mrkdwn 文字列）のみで構成されている通知メッセージに、`go-safe-cmd-runner` を参考にした以下の要素を追加する:
- 見出しへの絵文字付与による正常系/異常系の一目での判別
- サマリ情報と詳細情報の分離
- 詳細情報を格納する attachment への色付け（正常系=緑、異常系=赤の 2 色。`go-safe-cmd-runner` の green/yellow/red 3 色構成のうち、黄色に対応する明確な中間状態が bsky-cleaner には存在しないため 2 色構成とする）

チャンネル振り分けロジック（正常系/異常系 Webhook URL の選択、部分失敗を異常系として扱う扱い）は 0006 の AC-05〜AC-08 で確定済みであり、本タスクでは変更しない。attachment の色分けもこの既存の 2 分法（`failed := outcome.Err != nil || (outcome.Result != nil && len(outcome.Result.Failed) > 0)`）にそのまま従う。

### 1.2 目的（ゴール）

- Slack 通知の見出しを見ただけで正常系/異常系が判別できる
- 実行結果のサマリ（削除件数・失敗件数など）と、失敗した投稿ごとの詳細情報を視覚的に分離する
- 詳細情報のブロックに正常系=緑、異常系=赤の色を付け、Slack のメッセージ一覧上でも視認性を高める
- 既存のサニタイズ・マスキング・切り詰め・チャンネル振り分けロジックの保証（0006 の AC-14〜AC-21 等）を後退させない

## 2. スコープ

### In Scope

- **F-001**: 見出しへの絵文字付与による正常系/異常系の判別
- **F-002**: サマリ情報と詳細情報（失敗投稿一覧）の分離
- **F-003**: 詳細情報を格納する attachment への色付け（緑/赤の 2 色）
- **F-004**: 既存のサニタイズ・切り詰め・マスキング処理の新ペイロード構造への適用

### Out of Scope

- **黄色（警告）の中間状態表現**: 部分失敗は既存どおり異常系（赤）として扱う。黄色に対応する明確な要件（例: リトライ発生のみで最終的には成功、等）が現時点で存在しないため見送る
- **Run ID・ホスト名などの実行識別情報の付加**: `go-safe-cmd-runner` は Run ID/Hostname をトレーラフィールドとして付与しログとの相関に使うが、bsky-cleaner には Run ID の概念自体が存在せず、導入は `Outcome` 型の拡張を伴う別関心事のため見送る
- **Slack Block Kit（`blocks` フィールド）の採用**: `go-safe-cmd-runner` に倣い legacy attachments API（`attachments[].color` + `fields`）を使う。Block Kit への移行は本タスクの目的（色分け・絵文字・サマリ/詳細分離）に対して過剰であり見送る
- **通知先チャンネル振り分けロジックの変更**: 0006 の AC-05〜AC-08 で確定済みのロジックはそのまま使う

## 3. 機能要件と受け入れ基準

### F-001: 見出しへの絵文字付与

Slack メッセージの先頭（`text` フィールド）に、実行結果に応じた絵文字を付与する。

**Acceptance Criteria**:
- **AC-01**: 実行が正常終了した場合（削除失敗が 0 件かつ `outcome.Err == nil`）、見出しに成功を示す絵文字（例: `✅`）が付与される
- **AC-02**: 実行がエラー終了した場合（`outcome.Err != nil`、または `outcome.Result != nil && len(outcome.Result.Failed) > 0`）、見出しに失敗を示す絵文字（例: `❌`）が付与される

### F-002: サマリ情報と詳細情報の分離

現在 1 つのテキストブロックにまとめている「結果概要（成功/失敗、削除件数）」と「失敗した投稿ごとの詳細（rkey・エラー種別）」を分離する。サマリは見出し直下の `text` に残し、詳細は attachment の `fields` に格納する。

**Acceptance Criteria**:
- **AC-03**: メッセージの `text` には、実行結果の概要（成功/失敗、削除件数、失敗件数）のみが含まれ、失敗した投稿ごとの個別詳細は含まれない
- **AC-04**: 失敗した投稿が存在する場合、各投稿の rkey とエラー種別が attachment の `fields` に構造化フィールドとして格納される
- **AC-05**: 失敗した投稿が存在しない場合（完全成功）、詳細用の attachment（またはその `fields`）は生成されない、または空である

### F-003: 詳細情報 attachment への色付け

attachment に Slack legacy color（`good`/`danger`）を設定する。

**Acceptance Criteria**:
- **AC-06**: 実行が正常終了した場合、attachment の `color` に緑系の値（`good`）が設定される
- **AC-07**: 実行が異常終了した場合（部分失敗を含む）、attachment の `color` に赤系の値（`danger`）が設定される
- **AC-08**: attachment の色分けは、0006 の AC-05〜AC-08 で確定した通知先チャンネル振り分け（`failed` 判定式）と同一の条件式を使う（色分けとチャンネル振り分けの判定基準が乖離しない）

### F-004: 既存のサニタイズ・切り詰め・マスキングの継続適用

ペイロード構造が `{"text": "..."}` から `text` + `attachments` に変わっても、0006 で確立したセキュリティ上の保証を後退させない。

**Acceptance Criteria**:
- **AC-09**: attachment の `fields` に格納する rkey・エラー種別についても、既存の `sanitizeForPayload`（制御文字除去 + mrkdwn エスケープ）が適用される
- **AC-10**: ペイロード全体（`text` + `attachments` を含めた JSON 全体、または各テキストフィールド）が Slack の許容する上限長を超える場合、既存と同等の切り詰め方針（末尾切り詰め + 切り詰りを示すマーカー）が適用される。フィールド単位で切り詰める場合と全体で切り詰める場合のどちらを採るかは 02_architecture.md で決定する
- **AC-11**: 秘密情報（app パスワード・セッション JWT・`Authorization` ヘッダー値・Slack Webhook URL）が新しいペイロード構造のいずれのフィールドにも含まれない（0006 AC-19 の継続）
- **AC-12**: 投稿本文（body）そのものは新しいペイロード構造のいずれのフィールドにも含まれない（0006 AC-14 の継続）

## 4. 非機能要件

- **NF-001**: `make fmt`・`make test`・`make lint` が成功する。
- **NF-002**: 新しいペイロード構造の構築ロジックについて、Webhook への実際のネットワーク通信なしに単体テストできること（0006 NF-002 と同様の方針）。
- **NF-003**: 悪意あるペイロード（メンション記法、ANSI エスケープ、改行混入等）に対するセキュリティテストを維持し、`fields` を含む新構造でも 0006 の NF-003 相当の検証を行う。
- **NF-004**: Go 1.26.2 以上でビルドできること。
- **NF-005**: 既存の `make notify-preview` 開発者ツール（`docs/dev/developer_guide/notify_preview.md`）が新しいペイロード構造でも動作し、開発者が新フォーマットをローカルで確認できること。

## 5. スコープ外の根拠

- **黄色（警告）の中間状態**: ユーザー確認の結果、bsky-cleaner の実行結果は「完全成功」「一部失敗を含む異常系」の 2 分法（0006 AC-07）のみであり、`go-safe-cmd-runner` の 3 段階（success/warning/error）に対応する明確な「警告」状態が存在しないため、緑/赤の 2 色構成とする。将来的にリトライ発生時の警告表示等の要件が生じた場合は別タスクで再検討する。
- **Run ID・Hostname のトレーラフィールド**: `go-safe-cmd-runner` はログとの相関のためにこれらを付与するが、bsky-cleaner にはそもそも Run ID の概念がなく、ファイルログも持たない設計（[プロジェクト概要](../../overview.md)）のため、導入コストに対して本タスクのスコープ外とする。
- **Block Kit（`blocks`）への移行**: 色分け付き attachment という要求は legacy attachments API で過不足なく満たせるため、より複雑な Block Kit への移行は YAGNI の観点から見送る。

## 6. 成功基準（要約）

- AC-01〜AC-12 が test/static で緑。
- `--apply` 実行時、Slack 通知の見出しで正常系/異常系が絵文字により一目で判別でき、詳細情報（失敗投稿一覧）が緑/赤に色分けされた attachment として表示される状態。0006 で確立したサニタイズ・マスキング・チャンネル振り分けの保証は後退しない。
