## 1. 背景と目的

### 1.1 背景

[プロジェクト概要](../../overview.md) の「実行結果の通知」「Slack 通知における情報漏洩対策」、および [セキュリティ設計](../../design/security.md) の「投稿本文経由の間接的なインジェクション」にある通り、実行結果（正常系・異常系）を Slack Webhook 経由で通知する。投稿本文をそのまま通知に含めると、メンション拡散・ANSI エスケープ注入・ログ偽装のリスクがあるため、姉妹プロジェクト `go-safe-cmd-runner` と同様の対策を踏襲する。

正常系・異常系の通知先 Webhook URL はホスト部が一致している前提とし、不一致の場合は fail-closed で起動を失敗させる。

### 1.2 目的（ゴール）

- 実行結果（成功/失敗、削除件数等）を Slack に通知できる
- 正常系・異常系で異なるチャンネル（Webhook URL）に振り分けられる
- 投稿本文由来の内容を含む通知において、インジェクション・情報漏洩のリスクを排除する
- Webhook URL のホスト不一致を検知した場合、通知を諦めるのではなく起動自体を失敗させる

## 2. スコープ

### In Scope

- **F-001**: Slack Webhook への通知送信
- **F-002**: 実行モード（dry-run / apply）と通知タイミング
- **F-003**: 正常系/異常系チャンネルの振り分け
- **F-004**: Webhook 送信の HTTP 挙動（タイムアウト・送信失敗の扱い）
- **F-005**: Webhook URL のホスト一致検証（fail-closed）
- **F-006**: 通知内容のサニタイズ（メンション拡散・ANSI エスケープ・ログ偽装対策）
- **F-007**: 秘密情報のマスキング

### Out of Scope

- **Bluesky API 呼び出しのリトライ・実行タイムアウト**（[0005_retry_timeout](../0005_retry_timeout/01_requirements.md) の責務。本タスクは「リトライを含む実行結果」を受け取って通知する側であり、Bluesky 側のリトライ自体は実装しない）。ただし **Slack Webhook への POST の HTTP タイムアウト等は 0005 の責務外**であり、本タスク F-004 で扱う（両者は別のリトライ／タイムアウト関心事である）。
- CLI からの結果集約ロジック（[0004_cli_entrypoint](../0004_cli_entrypoint/01_requirements.md) の NF-005 で定義される構造化された実行結果データを入力として利用する）
- 通知メッセージの詳細フォーマット（attachment の色・絵文字・Run ID 等のリッチ表現）。[プロジェクト概要](../../overview.md) で「Slack 通知メッセージの内容・フォーマット」は後続検討とされているため、本タスクは送信・振り分け・サニタイズ・マスキングという基盤に専念し、フォーマットは最小限とする（姉妹プロジェクト `tlsrpt-digest` の attachment 形式を将来の参考とする）。

## 3. 機能要件と受け入れ基準

### F-001: Slack Webhook への通知送信

**Acceptance Criteria**:
- **AC-01**: 実行結果（成功/失敗、削除件数、失敗した投稿の識別子（AT URI/rkey 等）、エラー種別）を Slack Incoming Webhook 形式のペイロードとして送信できる
- **AC-02**: Webhook への送信が失敗した場合（ネットワークエラー等）、CLI 本体の終了コードは削除処理自体の成否のみを反映し、通知の送信失敗によって変化しない
- **AC-03**: 通知の送信に失敗した場合、その事実（失敗した旨）は標準エラー出力に出力される。ファイルログを持たない設計（[プロジェクト概要](../../overview.md)）のため、サイレント失敗を避ける目的で最低限 stderr に出力する。出力時に Webhook URL は秘匿情報としてマスクする（F-007）

### F-002: 実行モード（dry-run / apply）と通知タイミング

本ツールは dry-run をデフォルトとし、`--apply` 指定時のみ実際に削除する（[プロジェクト概要](../../overview.md)・[0004_cli_entrypoint](../0004_cli_entrypoint/01_requirements.md)）。デフォルト実行のたびに Slack へ投稿すると通知ノイズが大きいため、通知は実削除を行う `--apply` 実行に限定する。

**Acceptance Criteria**:
- **AC-04**: `--apply` 実行時のみ Slack 通知を送信する。デフォルト（dry-run）実行では Slack 通知を送信しない

### F-003: 正常系/異常系チャンネルの振り分け

以下の基準は F-002 の AC-04 を満たす場合（`--apply` 実行時）のみ適用される。

**Acceptance Criteria**:
- **AC-05**: 実行が正常終了した場合（削除失敗が 0 件）、正常系用の Webhook URL に通知が送信される
- **AC-06**: 実行がエラー終了した場合、異常系用の Webhook URL に通知が送信される
- **AC-07**: 削除対象の一部のみ失敗した場合（部分失敗）は、異常系（エラー終了）として扱い、異常系用の Webhook URL に送信する。すなわち「失敗が 1 件でもあれば異常系」とする
- **AC-08**: 正常系・異常系に同一の Webhook URL を設定した運用でも、正しく動作する（overview.md に明記された「同一チャンネルに統一する運用も可能」を満たす）

### F-004: Webhook 送信の HTTP 挙動（タイムアウト）

Slack Webhook への POST がハング・低速応答した場合でも、CLI 全体が無限にブロックしないようにする。特に本ツールは cron 定期実行を前提とし、[0005_retry_timeout](../0005_retry_timeout/01_requirements.md) の実行タイムアウト（多重起動対策）と整合する必要がある。

**Acceptance Criteria**:
- **AC-09**: Slack Webhook への HTTP POST には HTTP タイムアウトを設ける（無制限にブロックしない）
- **AC-10**: 通知処理全体（送信・リトライを行う場合はそれを含む）の最悪ケース所要時間は有界であり、[0005_retry_timeout](../0005_retry_timeout/01_requirements.md) が設定する実行タイムアウトより十分短くなるよう設計する（通知処理が実行タイムアウトを食い尽くさない）

### F-005: Webhook URL のホスト一致検証

**Acceptance Criteria**:
- **AC-11**: 正常系・異常系の Webhook URL のホスト部が一致する場合、設定は正常に読み込まれる
- **AC-12**: 正常系・異常系の Webhook URL のホスト部が一致しない場合、fail-closed で起動が失敗する（通知を送らずスキップするのではなく、明確なエラーで起動自体を止める）
- **AC-13**: ホスト部の照合はポート番号を除いた形で行い、大文字/小文字を区別しない完全一致とする（例: `https://host:443/...` のホスト部は `host` として照合する）

### F-006: 通知内容のサニタイズ

本タスクの通知には投稿本文（body）そのものは含めない。ただし、通知・コンソール出力に含める識別子やエラー由来の文字列（handle・DID・AT URI/rkey・サーバ由来のエラーメッセージ等）は外部から与えられうる値であり、メンション拡散・ANSI エスケープ・ログ偽装のリスクを持つため、これらに対して無条件にサニタイズを適用する。

**Acceptance Criteria**:
- **AC-14**: 通知ペイロードに投稿本文（body）そのものは含めない。含めるのは削除件数・成否・対象投稿の識別子（AT URI/rkey 等）・エラー種別といった構造化フィールドに限る
- **AC-15**: 通知に含める外部由来の文字列（識別子・エラーメッセージ等）は、Slack の `@channel` / `@here` 等のメンション記法が展開されない形式で送信される
- **AC-16**: 通知に含める外部由来の文字列は、ANSI エスケープシーケンスが除去またはエスケープされる
- **AC-17**: コンソール出力（CLI の標準出力）についても、外部由来の文字列にログ偽装（改行混入によるログ行の偽装）が起きないよう、改行等の制御文字が除去またはエスケープされる。サニタイズ処理（関数）は本タスクが提供し、標準出力への変換を担う [0004_cli_entrypoint](../0004_cli_entrypoint/01_requirements.md) がそれを呼び出す形で、サニタイズの実装を一箇所に集約する
- **AC-18**: 通知ペイロードが Slack の許容する上限長を超える場合、末尾を切り詰め、切り詰めが行われたことが分かるマーカー（例: `...`）を付与する。これにより、大量削除時にペイロード肥大化で Slack が送信を拒否し通知が失われる事態を防ぐ

### F-007: 秘密情報のマスキング

**Acceptance Criteria**:
- **AC-19**: 通知ペイロードおよび AC-03 の stderr 出力の構築過程で、app パスワード・セッション JWT・`Authorization` ヘッダーの値・**Slack Webhook URL** の値が含まれない（Webhook URL も秘匿情報として扱う。[プロジェクト概要](../../overview.md)・[0001_config](../0001_config/01_requirements.md) 準拠）
- **AC-20**: エラーオブジェクトをそのまま文字列化して通知に含めるような実装ではなく、通知に含めてよいフィールドを明示的に選択する形で構築される（構造体の丸ごと出力による秘密情報混入を防ぐ）

## 4. 非機能要件

- **NF-001**: `make fmt`・`make test`・`make lint` が成功する。
- **NF-002**: Webhook への実際のネットワーク通信なしに、通知ペイロードの構築・サニタイズ・ホスト検証・切り詰めロジックを単体テストできること。HTTP 挙動（タイムアウト・送信失敗時の stderr 出力）はモック HTTP サーバで検証できること。
- **NF-003**: サニタイズ・マスキング処理には、悪意あるペイロード（メンション記法、ANSI エスケープ、改行混入等）を用いたセキュリティテストが含まれること。秘匿情報（app パスワード・セッション JWT・`Authorization`・Webhook URL）が通知ペイロード・stderr 出力に含まれないことをテストで確認すること。
- **NF-004**: Go 1.26.2 以上でビルドできること。

## 5. スコープ外の根拠

- **Bluesky API のリトライ実行**自体は別タスク（[0005_retry_timeout](../0005_retry_timeout/01_requirements.md)）の責務であり、本タスクは実行結果を受け取って通知する下流の処理に専念する。なお **Slack Webhook POST の HTTP タイムアウト**は 0005 のスコープ外であるため本タスク F-004 が扱う（別のタイムアウト関心事である）。
- CLI からの結果集約は CLI エントリポイントタスクの責務であり、本タスクは [0004_cli_entrypoint](../0004_cli_entrypoint/01_requirements.md) の NF-005 で定義される構造化された実行結果データを受け取る形で実装する。
- **通知メッセージの詳細フォーマット（色・絵文字・Run ID 等）**は [プロジェクト概要](../../overview.md) で後続検討とされているため本タスクでは扱わない。姉妹プロジェクト `tlsrpt-digest` の attachment ベースのリッチ表現を将来の参考実装とする。
- **ホスト検証は正常系/異常系 2 URL の相互一致のみ**で行い、許可ホスト名の allowlist（`tlsrpt-digest` の `allowed_host` 相当）は本タスクでは採用しない（[プロジェクト概要](../../overview.md) の方針に従う）。相互一致で防げない誤送信（両 URL を同一の意図しないホストに向けた場合）に対する追加防御が必要になった場合は、[0008_security_hardening](../0008_security_hardening/) で再検討する。

## 6. 成功基準（要約）

- AC-01〜AC-20 が test/static で緑。
- `--apply` 実行時に、実行結果が正常系/異常系（部分失敗含む）に応じた Slack チャンネルに、秘密情報漏洩・インジェクションのリスクなく通知される状態。dry-run（デフォルト）実行では通知が送信されない状態。
