## 1. 背景と目的

### 1.1 背景

[プロジェクト概要](../../overview.md) の「実行結果の通知」「Slack 通知における情報漏洩対策」、および [セキュリティ設計](../../design/security.md) の「投稿本文経由の間接的なインジェクション」にある通り、実行結果（正常系・異常系）を Slack Webhook 経由で通知する。投稿本文をそのまま通知に含めると、メンション拡散・ANSI エスケープ注入・ログ偽装のリスクがあるため、姉妹プロジェクト `go-safe-cmd-runner` と同様の対策を踏襲する。

正常系・異常系の通知先 Webhook URL はホスト部が一致している前提とし、不一致の場合は fail-closed で起動を失敗させる。

### 1.2 目的（ゴール）

- 実行結果（成功/失敗、削除件数等）を Slack に通知できる
- 正常系・異常系で異なるチャンネル（Webhook URL）に振り分けられる
- 投稿本文由来の内容を含む通知において、インジェクション・情報漏洩のリスクを排除する
- Webhook URL のホスト不一致を検知した場合、通知を諦めるのではなく起動自体を失敗させる

## 2. スコープ

### In Scope

- **F-001**: Slack Webhook への通知送信
- **F-002**: 正常系/異常系チャンネルの振り分け
- **F-003**: Webhook URL のホスト一致検証（fail-closed）
- **F-004**: 通知内容のサニタイズ（メンション拡散・ANSI エスケープ・ログ偽装対策）
- **F-005**: 秘密情報のマスキング

### Out of Scope

- リトライ実行そのもの（[0005_retry_timeout](../0005_retry_timeout/01_requirements.md) の責務。本タスクは「リトライを含む実行結果」を受け取って通知する側であり、リトライ自体は実装しない）
- CLI からの結果集約ロジック（[0004_cli_entrypoint](../0004_cli_entrypoint/01_requirements.md) で作られる実行結果データを入力として利用する）

## 3. 機能要件と受け入れ基準

各機能要件には、独立して検証可能な受け入れ基準（Acceptance Criteria）を明示すること。
AC の採番ルールは [requirements_process.md](../../dev/developer_guide/requirements_process.md) を参照。

### F-001: Slack Webhook への通知送信

**Acceptance Criteria**:
- **AC-01**: 実行結果（成功/失敗、削除件数、対象投稿の概要等）を Slack Incoming Webhook 形式のペイロードとして送信できる
- **AC-02**: Webhook への送信が失敗した場合（ネットワークエラー等）、CLI 本体の終了コードには影響を与えない、またはドキュメント上明記された挙動に従う（通知失敗で削除処理自体の成否判定を覆さない）

### F-002: 正常系/異常系チャンネルの振り分け

**Acceptance Criteria**:
- **AC-03**: 実行が正常終了した場合、正常系用の Webhook URL に通知が送信される
- **AC-04**: 実行がエラー終了した場合、異常系用の Webhook URL に通知が送信される
- **AC-05**: 正常系・異常系に同一の Webhook URL を設定した運用でも、正しく動作する（overview.md に明記された「同一チャンネルに統一する運用も可能」を満たす）

### F-003: Webhook URL のホスト一致検証

**Acceptance Criteria**:
- **AC-06**: 正常系・異常系の Webhook URL のホスト部が一致する場合、設定は正常に読み込まれる
- **AC-07**: 正常系・異常系の Webhook URL のホスト部が一致しない場合、fail-closed で起動が失敗する（通知を送らずスキップするのではなく、明確なエラーで起動自体を止める）

### F-004: 通知内容のサニタイズ

**Acceptance Criteria**:
- **AC-08**: 通知内容に投稿本文由来のテキストを含める場合、Slack の `@channel` / `@here` 等のメンション記法が展開されない形式で送信される
- **AC-09**: 通知内容に投稿本文由来のテキストを含める場合、ANSI エスケープシーケンスが除去またはエスケープされる
- **AC-10**: コンソール出力（CLI の標準出力）についても、投稿本文由来のテキストにログ偽装（改行混入によるログ行の偽装）が起きないよう、改行等の制御文字が除去またはエスケープされる

### F-005: 秘密情報のマスキング

**Acceptance Criteria**:
- **AC-11**: 通知ペイロードの構築過程で、app パスワード・セッション JWT・`Authorization` ヘッダーの値が含まれない
- **AC-12**: エラーオブジェクトをそのまま文字列化して通知に含めるような実装ではなく、通知に含めてよいフィールドを明示的に選択する形で構築される（構造体の丸ごと出力による秘密情報混入を防ぐ）

## 4. 非機能要件

必要に応じて `NF-XXX` の識別子を付け、実装計画書からの参照を可能にする。

- **NF-001**: `make fmt`・`make test`・`make lint` が成功する。
- **NF-002**: Webhook への実際のネットワーク通信なしに、通知ペイロードの構築・サニタイズ・ホスト検証ロジックを単体テストできること。
- **NF-003**: サニタイズ・マスキング処理には、悪意あるペイロード（メンション記法、ANSI エスケープ、改行混入等）を用いたセキュリティテストが含まれること。
- **NF-004**: Go 1.26.2 以上でビルドできること。

## 5. スコープ外の根拠

- リトライの実行自体は別タスクの責務であり、本タスクは実行結果を受け取って通知する下流の処理に専念する。
- CLI からの結果集約は CLI エントリポイントタスクの責務であり、本タスクは通知に必要なデータ構造（インターフェース）を定義し、それを受け取る形で実装する。

## 6. 成功基準（要約）

- AC-01〜AC-12 が test/static で緑。
- 実行結果が正常系/異常系に応じた Slack チャンネルに、秘密情報漏洩・インジェクションのリスクなく通知される状態。
