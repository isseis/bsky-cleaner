## 1. 背景と目的

### 1.1 背景

[プロジェクト概要](../../overview.md) の「使用する API」および「外部依存の最小化」方針にある通り、本ツールが Bluesky（AT Protocol）とやり取りするために必要なエンドポイントはログイン・一覧取得・削除の 3 つに限られる。`indigo` のような大きな SDK を導入せず、薄い自作 XRPC クライアントを実装する。

DID 解決・PDS エンドポイント決定ロジックは、実装を誤ると app パスワードやセッショントークンを意図しないホストへ送信してしまう（実質的な SSRF）ため、[セキュリティ設計](../../design/security.md) のリスクカテゴリとして特に慎重な設計が要る。

本タスクは [0001_config](../0001_config/01_requirements.md) が提供する設定（app パスワード等）を前提とする。

### 1.2 目的（ゴール）

- app パスワードでログインし、セッションを取得できる
- 自分の投稿一覧（通常投稿・リプライ・リポスト・引用ポスト、ピン留め状態を含む）を取得できる
- 指定した投稿（rkey）を削除できる
- 上記すべてを、DID 解決を経由した正しい PDS エンドポイントに対して安全に実行できる

## 2. スコープ

### In Scope

- **F-001**: DID 解決による PDS エンドポイントの決定
- **F-002**: `com.atproto.server.createSession` によるログイン（セッション取得）
- **F-003**: 投稿一覧の取得（`listRecords` または `getAuthorFeed`）
- **F-004**: `com.atproto.repo.deleteRecord` による投稿削除
- **F-005**: エラーハンドリング（秘密情報を含まないエラー型）

### Out of Scope

- リトライ・指数バックオフ（[0005_retry_timeout](../0005_retry_timeout/01_requirements.md) で扱う。クライアントの単一呼び出しの正しさとリトライ戦略は別関心事のため）
- 投稿の経過日数・種別によるフィルタリングロジック（[0003_cleanup_engine](../0003_cleanup_engine/01_requirements.md) で扱う。クライアントはデータ取得に専念し、ビジネスロジックとは分離する）
- CLI からの呼び出し・dry-run/apply の切り替え（[0004_cli_entrypoint](../0004_cli_entrypoint/01_requirements.md) で扱う）

## 3. 機能要件と受け入れ基準

### F-001: DID 解決による PDS エンドポイントの決定

アカウントの DID を解決し、そのアカウントが実際にデータを保持する PDS のエンドポイントを安全に決定する。

**Acceptance Criteria**:
- **AC-01**: handle または DID からアカウントの DID ドキュメントを取得し、PDS のサービスエンドポイントを抽出できる
- **AC-02**: DID ドキュメントの解決先が想定外のスキーム（`https` 以外）を返した場合、fail-closed で処理を中断する
- **AC-03**: DID 解決結果のホストが信頼できない、または解決に失敗した場合、app パスワードを含むリクエストを一切送信せずに処理を中断する（SSRF 対策）

### F-002: ログイン（セッション取得）

`com.atproto.server.createSession` に app パスワードを送信し、以降の API 呼び出しに使うセッション（アクセス JWT）を取得する。

**Acceptance Criteria**:
- **AC-04**: 正しい handle と app パスワードでログインした場合、セッション情報（アクセス JWT 等）を取得できる
- **AC-05**: 認証情報が誤っている場合、エラーが返り、後続の API 呼び出しは行われない
- **AC-06**: ログイン処理で発生したエラーオブジェクトの文字列表現に、送信した app パスワードやレスポンスに含まれるセッション JWT が含まれない

### F-003: 投稿一覧の取得

対象アカウントの投稿一覧を取得する。各投稿について、少なくとも rkey、種別（通常投稿/リプライ/リポスト/引用ポスト）、作成日時（`createdAt`）、ピン留め状態を判定できる情報を含む。

**Acceptance Criteria**:
- **AC-07**: 投稿が存在する場合、一覧取得 API を呼び出し、各投稿の rkey・種別・`createdAt` を取得できる
- **AC-08**: ページネーションが必要な件数の投稿がある場合、全件を取得できる（カーソルを辿り最後まで収集する）
- **AC-09**: ピン留めされた投稿を、一覧上で判別できる形で取得できる
- **AC-10**: 投稿が 0 件のアカウントに対しては、エラーにならず空の一覧を返す

### F-004: 投稿削除

指定した rkey の投稿を `com.atproto.repo.deleteRecord` で削除する。

**Acceptance Criteria**:
- **AC-11**: 存在する rkey を指定した場合、該当レコードが削除される
- **AC-12**: 既に削除済みの rkey を指定した場合（一覧取得後に別経路で削除された等）、クラッシュせず正常系として扱われる（冪等性の確保）
- **AC-13**: 削除対象でない他アカウントのレコードを指定できないよう、認証済みセッションに紐づくリポジトリに対してのみ削除が実行される

### F-005: エラーハンドリング

**Acceptance Criteria**:
- **AC-14**: HTTP レベルのエラー（タイムアウト、5xx 応答等）が、呼び出し元が `errors.Is` / `errors.AsType[T]` で判別可能な型付きエラーとして返る
- **AC-15**: いかなるエラーパスにおいても、`Authorization` ヘッダーの値・app パスワード・セッション JWT がエラーオブジェクトの文字列表現に含まれない

## 4. 非機能要件

- **NF-001**: `make fmt`・`make test`・`make lint` が成功する。
- **NF-002**: 外部依存を最小化し、HTTP 通信は標準ライブラリ（`net/http`）ベースの薄い自作実装とする（`indigo` 等の大型 SDK を導入しない）。
- **NF-003**: DID 解決・PDS 通信は SSRF を防ぐため、リダイレクトの扱いも含めて意図しないホストへの通信が発生しないこと。
- **NF-004**: HTTP 通信部分はインターフェース化し、実際のネットワーク通信を伴わない単体テストが可能であること。
- **NF-005**: Go 1.26.2 以上でビルドできること。

## 5. スコープ外の根拠

- リトライは、単一の API 呼び出しが「何を・どう送るか」というクライアントの責務と、「失敗時にどう振る舞うか」という横断的関心事が異なるため分離する。クライアントのインターフェースはリトライ層から呼び出される前提で設計する。
- フィルタリングロジックはクライアントが返す生データに依存する下流の処理であり、クライアント自体の責務ではない。
- CLI からの結線は、設定・クライアント・エンジンが揃った後にまとめて行う。

## 6. 成功基準（要約）

- AC-01〜AC-15 が test/static で緑。
- ログイン・投稿一覧取得・投稿削除の 3 操作が、SSRF・秘密情報漏洩のリスクを回避した形で実装されている状態。
