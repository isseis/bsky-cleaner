## 1. 背景と目的

### 1.1 背景

[プロジェクト概要](../../overview.md) の「リトライ方針」「セキュリティ考慮事項」および [セキュリティ設計](../../design/security.md) にある通り、API 呼び出しの失敗に対しては指数バックオフでリトライしつつ、上限のないリトライは Bluesky 側のレート制限・アカウント制限を誘発しうる。また、cron による定期実行を前提とするため、処理が長引いた場合に次回起動と重複しないよう、実行タイムアウトによる多重起動対策が必要となる。

本タスクは [0002_atproto_client](../0002_atproto_client/01_requirements.md) が提供する単一呼び出しのクライアントに対し、リトライ・タイムアウトという横断的関心事を追加する。

### 1.2 目的（ゴール）

- API 呼び出し失敗時に、上限付きの指数バックオフでリトライする
- 実行全体に対してタイムアウトを設け、多重起動によるリソース競合を防ぐ
- タイムアウトにより削除呼び出しが強制中断されても、冪等性を前提に安全側に倒れ、完了/未完了（成否不明を含む）を判別できる形で結果を返す

## 2. スコープ

### In Scope

- **F-001**: API 呼び出し失敗時の指数バックオフ付きリトライ
- **F-002**: 実行全体の実行タイムアウト
- **F-003**: タイムアウトと削除処理の境界制御（冪等性・中途半端な状態の回避）

### Out of Scope

- ロックファイル等による排他制御（[セキュリティ設計](../../design/security.md) に「実装の単純さを優先し採用しない」と明記されている。実行タイムアウトのみで多重起動対策とする）
- Slack 通知でのリトライ失敗時の通知内容（[0006_slack_notification](../0006_slack_notification/01_requirements.md) で扱う）
- cron のスケジュール間隔の値そのもの（利用者が [0001_config](../0001_config/01_requirements.md) の TOML `schedule` に設定する値であり、いずれのタスクもその大小を決定・検証しない。本タスクはタイムアウト値が、利用者が設定した間隔より十分短くなるよう設計する責務のみを持つ）
- 個々の XRPC 呼び出しに対する専用のリクエスト全体タイムアウト（`http.Client.Timeout` 等）の実装。実行タイムアウトの deadline を個々の呼び出しの `context.Context` へ伝播させる（AC-08）ことで、低速応答（slowloris 的挙動）によるハングも実行タイムアウトの範囲に収まるため、本タスクでは専用の上限は設けない

## 3. 機能要件と受け入れ基準

### F-001: 指数バックオフ付きリトライ

**Acceptance Criteria**:
- **AC-01**: API 呼び出しが一時的なエラー（5xx、タイムアウト等）で失敗した場合、指数バックオフで待機した上で再試行する
- **AC-02**: リトライ回数が設定された上限に達した場合、それ以上リトライせずエラーとして呼び出し元に返す
- **AC-03**: 認証エラー（401 等）のような再試行しても解決しないエラーに対しては、リトライせず即座にエラーを返す
- **AC-04**: リトライ間の待機時間には上限（最大バックオフ時間）が設けられており、無制限に増加しない

### F-002: 実行全体の実行タイムアウト

**Acceptance Criteria**:
- **AC-05**: 設定された実行タイムアウトを超過した場合、処理を中断し、明確なタイムアウトエラーとして終了する
- **AC-06**: 実行タイムアウトは [0001_config](../0001_config/01_requirements.md) で読み込まれる設定値から取得される
- **AC-07**: タイムアウトの累積時間見積もりに、リトライの最悪ケース（最大リトライ回数 × 最大バックオフ時間）が考慮されていることがドキュメント上明記されている（static 検証）

### F-003: タイムアウトと削除処理の境界制御

**Acceptance Criteria**:
- **AC-08**: 実行タイムアウトの deadline は個々の削除 API 呼び出しの `context.Context` にも伝播し、呼び出し中にタイムアウトへ達した場合はその呼び出しを強制中断してよい。ただし強制中断された呼び出しの投稿は「削除完了」として扱わず、削除の成否が確認できない投稿として扱う
- **AC-09**: タイムアウトにより処理が中断した場合、それまでに削除完了が確認できた投稿と、削除が未完了・成否不明なまま残った投稿（強制中断されたものを含む）が判別できる形で結果が返る

**注記**: 強制中断された投稿を「未完了」として扱うことの安全性は、`DeleteRecord` の冪等性（[0002_atproto_client](../0002_atproto_client/01_requirements.md) AC-12）に依拠する。次回実行時に同じ投稿への削除を再試行しても、サーバー側で既に削除が完了していた場合は安全に成功応答が返る。

## 4. 非機能要件

- **NF-001**: `make fmt`・`make test`・`make lint` が成功する。
- **NF-002**: リトライ・タイムアウトのロジックは、実際の HTTP 通信や `time.Sleep` の実時間待機なしに単体テストできること（時間のモック化）。
- **NF-003**: `context.Context` を用いてタイムアウト・キャンセルを伝播させること。
- **NF-004**: Go 1.26.2 以上でビルドできること。

## 5. スコープ外の根拠

- ロックファイルによる排他制御は、セキュリティ設計文書で「実装の単純さを優先し採用しない」と明示的に決定済みのため対象外。
- Slack 通知内容の設計は通知タスク固有の関心事。
- cron スケジュール間隔の値は利用者が TOML の `schedule` に設定するものであり、いずれのタスクもその値自体を決定・検証しない。本タスクはタイムアウト値を「利用者が設定した間隔より十分短くする」という制約を満たすように設計する側の責務のみを負う。
- **ロックファイル非採用の安全性の前提**: 実行タイムアウトのみで多重起動を防ぐ本方針は、`DeleteRecord` が冪等であること（[0002_atproto_client](../0002_atproto_client/01_requirements.md) AC-12 で検証済み。存在しない・削除済みの rkey を指定しても成功応答が返る）を前提としている。この前提の下では、タイムアウト超過による cron 起動の重複が発生しても、削除処理自体はデータ破壊（誤削除・二重削除によるエラー）を起こさない安全側に倒れる。ただし、重複起動は API 呼び出し数の増加によるレート制限リスクの増幅、および（[0006_slack_notification](../0006_slack_notification/01_requirements.md) スコープだが）通知内容の重複という副作用を許容した上での設計判断であり、これらの副作用自体を防止する対策は本タスクのスコープ外とする。

## 6. 成功基準（要約）

- AC-01〜AC-09 が test/static で緑。
- API 呼び出しの一時的な失敗に対して上限付きでリトライしつつ、実行全体が設定されたタイムアウト内に収まり、多重起動を防げる状態。
