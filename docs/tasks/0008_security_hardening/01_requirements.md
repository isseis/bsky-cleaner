## 1. 背景と目的

### 1.1 背景

[0001_config](../0001_config/01_requirements.md) 〜 [0007_docker_distribution](../0007_docker_distribution/01_requirements.md) の各タスクは、それぞれの範囲内でセキュリティ要件（AC）を定義・実装する。しかし、[セキュリティ設計](../../design/security.md) に挙げられたリスクカテゴリの中には、複数コンポーネントを横断して初めて確認できる項目（例: エンドツーエンドでの秘密情報非漏洩、削除処理全体の冪等性）が含まれる。本タスクは、初期リリース前の最終工程として、これらの横断的なセキュリティ項目を統合的に検証・強化する。

本タスクは [0001_config](../0001_config/01_requirements.md) 〜 [0007_docker_distribution](../0007_docker_distribution/01_requirements.md) すべてが完了していることを前提とする。

### 1.2 目的（ゴール）

- コンポーネント単体テストでは検出できない、統合後のエンドツーエンドの秘密情報漏洩がないことを確認する
- [セキュリティ設計](../../design/security.md) に挙げられた各リスクカテゴリについて、対策の実装状況を棚卸しし、抜け漏れを解消する
- 削除処理全体（一覧取得〜削除実行〜通知）を通した冪等性・異常系の挙動を統合的に検証する

## 2. スコープ

### In Scope

- **F-001**: エンドツーエンドでの秘密情報非漏洩の統合テスト
- **F-002**: セキュリティ設計文書に対する実装状況の棚卸しと抜け漏れ対応
- **F-003**: 削除処理全体を通した冪等性・異常系シナリオの統合テスト

### Out of Scope

- 個別コンポーネントの新規機能追加（各タスク（0001〜0007）で完結しているべきであり、本タスクは既存実装の検証・強化に専念する）。ただし security.md に「防御が抜けている」と明記された既知のセキュリティ穴の是正は「抜け漏れの解消」（1.2）に含まれ、新規機能追加とはみなさない。当該項目を本タスクで実装するか元タスクへ差し戻すかは AC-04 で決着させる
- 設定ファイルのファイルシステム権限管理・改ざん検知の実装（overview.md の「未確定・今後検討する事項」に挙げられており、初期リリースの完了の定義には含まれないため、本タスクでも棚卸しの対象とはするが実装は対象外とする）

## 3. 機能要件と受け入れ基準

### F-001: エンドツーエンドでの秘密情報非漏洩

秘密情報とは、app パスワード・セッション JWT・`Authorization` ヘッダーの値、および Slack Webhook URL を指す（Webhook URL は [overview.md](../../overview.md) の通り app パスワードと同様の秘匿情報として扱う）。

**Acceptance Criteria**:
- **AC-01**: 設定読み込みからログイン・一覧取得・削除・Slack 通知までを通した統合テストにおいて、標準出力・標準エラー出力・Slack 通知ペイロードのいずれにも上記の秘密情報の値が含まれないことを検証する
- **AC-02**: 次の代表的なエラー経路それぞれについて、意図的にエラーを発生させたうえで AC-01 と同様に秘密情報が含まれないことを検証する: (a) 認証失敗（`createSession` エラー）、(b) ネットワークエラー、(c) DID/PDS エンドポイント解決エラー、(d) 削除呼び出しの失敗、(e) Slack 通知の送信失敗、(f) 実行タイムアウト到達

### F-002: セキュリティ設計文書に対する実装状況の棚卸し

**Acceptance Criteria**:
- **AC-03**: [セキュリティ設計](../../design/security.md) に列挙された各リスクカテゴリ（投稿本文経由のインジェクション、SSRF、壊れた・攻撃者管理下の PDS 起因のリソース枯渇（DoS）、秘密情報漏洩、リトライ過多、多重起動、設定改ざん、削除処理の冪等性、Docker サプライチェーン）について、対応する実装・テストへのトレーサビリティが本タスクの実装計画書に一覧化されている。列挙が security.md と乖離しないよう、棚卸し対象は security.md の記載を正とする
- **AC-04**: 棚卸しの結果、対策が未実装または不十分と判明した項目について、本タスク内で対応するか、対応しない場合はその理由が明記される。特に security.md が現時点で未対策と明記している DoS 系の3項目（`doXRPC` のレスポンスサイズ上限、`listAllRecords` の総ページ/総レコード上限、XRPC `http.Client` のリクエスト全体タイムアウト）については、本タスクで実装するか 0002/0005 へ差し戻すかを明示的に決着させる

### F-003: 削除処理全体を通した冪等性・異常系シナリオ

**Acceptance Criteria**:
- **AC-05**: 一覧取得後、削除実行までの間に対象投稿が既に削除されていた場合でも、処理全体がクラッシュせず正常系として扱われることを統合テストで検証する
- **AC-06**: 実行タイムアウトが処理途中で発生した場合でも、それまでに削除済みの投稿と未処理の投稿が判別可能な形で結果が得られ、次回実行時に重複削除の試行によってエラーにならないことを検証する。この安全性は `DeleteRecord` の冪等性（[0002_atproto_client](../0002_atproto_client/01_requirements.md) AC-12）および実行タイムアウトの強行中断の扱い（[0005_retry_timeout](../0005_retry_timeout/01_requirements.md) AC-08・AC-09）に依拠する

## 4. 非機能要件

- **NF-001**: `make fmt`・`make test`・`make lint` が成功する。
- **NF-002**: 統合テストは実際の Bluesky API に依存せず、モック/フェイクサーバーを用いて再現可能であること。
- **NF-003**: Go 1.26.2 以上でビルドできる。

## 5. スコープ外の根拠

- 個別コンポーネントの機能実装は各タスク（0001〜0007）の責務であり、本タスクは横断的な検証・棚卸しに専念することで責務を明確に分離する。
- ファイルシステム権限管理は、実装コストと必要性のバランスから初期リリースの完了の定義に含まれておらず、本タスクでも棚卸し（記録）のみを行い実装はしない。

## 6. 成功基準（要約）

- AC-01〜AC-06 が test/static で緑。
- [セキュリティ設計](../../design/security.md) の全リスクカテゴリについて対応状況がトレース可能であり、各実装統合後のエンドツーエンドの秘密情報漏洩・冪等性の問題がないことが確認された状態。
