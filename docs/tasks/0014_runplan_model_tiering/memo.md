# runplan.md モデル使い分け（tiering）評価メモ

## Status

`draft` — 正式な機能タスクではなく、`runplan.md` ワークフローの運用改善を検討するための試行的な記録。`01_requirements.md`/`02_architecture.md`/`03_implementation_plan.md` の定型フォーマットは使わない。

## 背景

`0013_slack_notification_context` の残作業（フェーズ7〜12）を進める際、以下を議論した。

- `runplan.md` は現状、コマンドを実行したモデル1つがオーケストレーションと実装コードの作成を両方担っている。
- ステップの中には難易度が常に低いもの（例: step 1 のタスク識別、step 11/12 のドキュメント対訳追加）と、フェーズの内容によって難易度が変動するもの（例: step 5 の実装、特に `cmd/main.go` のようなエラー伝播・計測区間が絡む変更）がある。
- `runplan.md` にはすでに step 6.5（決定的な静的チェック）と step 7（シニアレビュー subagent によるレビュー）という、弱いモデルの出力を強いモデルが検証するゲートが存在する。このため、実装（step 5）を難易度に応じて軽量モデルに委譲しても、品質の安全網はある程度確保できるのではないか、という仮説を立てた。

## 仮説

オーケストレーション（step 1-4, 6-8 の判断部分）は上位モデルに残しつつ、以下の基準で委譲すれば品質を落とさず速度・コストを改善できる可能性がある。

- **常に軽量モデルでよい候補**: 機械的な調査・パターンマッチのみのステップ（例: task identification、対訳ドキュメントの追記のような低リスクな文書作業）。
- **難易度評価が必要な候補**: step 5（フェーズ実装）。ファイル数、パッケージ横断かどうか、エラーハンドリング/セキュリティ関連（シークレット、認証、リトライ、通知配信保証など）に触れるかどうかで難易度を判定し、モデルを選ぶ。
- **常に上位モデルに残すべき候補**: フェーズのグルーピング判断（step 4）、PR境界設計（step 2.5, `/mkplan2`）、レビュー（step 7）— 判断ミスが後続に連鎖するため。

## 注意点・リスク

- **サブエージェント起動のコールドスタートコスト**: `Agent` ツール経由でモデルを切り替えるしかなく、都度コンテキスト（`02_architecture.md`、既存コードのスタイル等）を自己完結したプロンプトで渡す必要がある。単純なステップではこのオーバーヘッドが節約分を上回る可能性がある。
- **速度 vs コスト**: サブエージェント往復のレイテンシにより、体感速度はむしろ悪化する場合がある。改善が主に見込めるのはコスト面。
- **難易度判定の誤り**: 判定を誤って軽量モデルに投げると、review subagent（step 7）での手戻りが発生し、結果的に上位モデルの時間を消費して逆効果になりうる。

   - フェーズ7（`cmd/main.go` 配線・新規テスト）: Sonnet（エラー伝播・計測区間など判断が絡むため）
   - フェーズ8〜10（`notifypreview` フィクスチャ・テスト総仕上げ・実送信確認）: 実装量に応じてその場で判定

## メモ自体の編集で発生した Markdown 崩れ（担当者本人によるミス、修正コミット 3a982906e54f343cdcc178c3c792b65424c4ce40）

フェーズ11の記録行を追記した際（本メモの担当者、Sonnet 本人による直接編集。Haiku委譲ではない）、テーブル内に空行を挟んでしまい、Markdown のテーブルレンダリングが2つに分断される崩れを起こした。ユーザーが手動で気づいて空行を削除し、修正した。

- **重要な事実**: これはHaiku委譲を試した箇所ではなく、Sonnet自身が直接書いたメモ本文で発生した単純な書式ミスである。モデルの階層化とは無関係に、レビュー（discovery review・self-check）の対象がコード変更にほぼ限定されており、`03_implementation_plan.md`・このメモのような**プロセス系ドキュメントの編集そのものは自己検証の対象外になりがち**という運用上の盲点を示す実例になった。
- **示唆**: Markdown編集後は `git diff` で差分を目視確認する、あるいはテーブルを含む差分では意図しない空行挿入が無いかを機械的にチェックする一手間を、コード変更と同様にドキュメント編集にも適用すべき（`make fmt` に相当する仕組みがコードにはあるが、Markdown 側には無いため、目視確認に頼らざるを得ない）。

## PR-5 レビューコメントで判明した見落とし（フェーズ7/8-10 discovery review 双方の盲点）

PR #133（フェーズ7〜10）に対する人間レビュアーのコメントで、`cmd/main_test.go` の `slackAttachmentFields` が「hooks.slack.com 宛リクエストが1件であることをアサートせず、最初にマッチしたリクエストを黙って返す」というバグを指摘された（複数の Slack リクエストが送られる回帰や、誤ったペイロードを検証してしまう回帰を検出できなくなる）。

- **重要な事実**: このバグはフェーズ7のSonnetによる discovery review（`review-subagent-pattern.md` の初回パス）でも、フェーズ8-10のSonnet discovery review・Haiku verification review でも検出されなかった。3回のAIレビューをすべてすり抜け、人間のレビュアーが指摘するまで気づかれなかった。
- **示唆**: 今回のモデル階層化実験は「実装フェーズにどのモデルを割り当てるか」「verification passを軽量モデルに委譲できるか」を検証してきたが、**discovery review自体の再現率（recall）はモデルの選択と独立に上限がある**ことを示す実例になった。`review-subagent-pattern.md` が明記する通り、discovery reviewはコストを削ってはいけない（recallが命）というルールだが、Sonnetでもこの種の「ヘルパー関数の暗黙の前提（複数マッチしうるのに1件だけ返す）」は見逃しうる。モデル階層化の効果測定とは別に、レビュー観点リスト自体に「テストヘルパーが暗黙に前提とする一意性・網羅性」を明示的に含めることを今後検討する価値がある。

## 総括（0013 フェーズ7〜12 完了時点）

`0013_slack_notification_context` の残フェーズ全体（PR-5〜PR-7）を通じて試した範囲での結論。

1. **難易度に応じたモデル選択という当初の仮説は支持された**: 判断が絡む実装（フェーズ7の `cmd/main.go` 配線）はSonnetで安定して低指摘数、解釈の自由度が低い純粋作業（フェーズ12、文言確定済みの追記）はHaikuで無指摘、解釈の自由度がある文書作業（フェーズ11、実装挙動の要約が必要）はHaikuでも実装自体は概ね正確だが編集品質・事実の網羅性でSonnetのdiscovery reviewが実際に手直しした。**「委譲するタスクの解釈の自由度」が、モデル選択の妥当性を左右する主要な軸だと分かった。**
2. **verification passの軽量モデル委譲は明確に機能した**（フェーズ8-10）。「すでに特定された修正が正しく適用されたか」という狭い確認作業はHaikuで十分。
3. **discovery reviewの再現率はモデル選択と独立に上限がある**——Sonnetで実施したdiscovery reviewが3回とも見逃した `slackAttachmentFields` の一意性バグを、最終的に人間のレビュアーが発見した。モデル階層化はコストと速度の最適化には有効だが、レビュー品質そのものの上限を引き上げる手段ではない。
4. **プロセス系ドキュメント（このメモや `03_implementation_plan.md` 自体）はレビュー・self-checkの対象から漏れやすい**——Markdownテーブル崩れが実例。
5. **同一の事実（`hostname` の空文字列・空白のみの扱い）が複数ファイルに分散していると、1箇所を直しても他が取り残される**——`configuration.md`/`.ja.md` の修正後に `package_reference.md` でも同じ曖昧さが見つかった。
