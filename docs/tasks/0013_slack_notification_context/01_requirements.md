## 1. 背景と目的

### 1.1 背景

[0012_slack_rich_formatting](../0012_slack_rich_formatting/01_requirements.md) で Slack 通知のペイロードを `text` + `attachments`（絵文字付き見出し・サマリ/詳細分離・色付け）に拡張した。同タスクの要件定義書は「Run ID・ホスト名などの実行識別情報の付加」を明示的に Out of Scope としている（同ドキュメント 2 節・5 節。理由: `Outcome` 型の拡張を伴う別関心事のため）。

現状の通知メッセージには、どのホスト／どの bsky アカウントの実行結果かを示す情報が一切無い。単一の Slack チャンネルに複数の bsky-cleaner インスタンス（例: 複数アカウントを別ホストで運用するケース）が通知を送る運用では、どの実行が問題を起こしたのかメッセージから特定できない。また、削除対象件数・実削除件数・処理時間といった統計情報も欠けており、実行結果の規模感を通知だけから把握できない。

本タスクは 0012 が見送ったこの「実行識別情報の付加」を実施するとともに、統計情報の追加も合わせて行う。

### 1.2 目的（ゴール）

- Slack 通知だけで「どのホスト・どの bsky アカウントの実行結果か」を正常系・異常系を問わず判別できる
- 削除処理まで到達した実行については、対象件数・削除件数・処理時間が通知から分かる
- 統計情報を構造化フィールド（`attachments[].fields`）に集約し、`text` の一行サマリから件数表現の重複を無くす

## 2. スコープ

### In Scope

- **F-001**: 実行ホスト・bsky アカウントの識別情報を、正常系・異常系共通で通知に含める
- **F-002**: 削除対象件数・削除件数・処理時間を統計情報として通知に含める（削除処理に到達しなかった実行では非表示）
- **F-003**: `text` のサマリ文言から件数表現を除去する（件数は `fields` に一本化する）

### Out of Scope

- **PDS ホスト（AT Protocol 接続先）の付加**: 本タスクで言う「ホスト」は bsky-cleaner を実行している計算機（オペレーターが運用上識別したいホスト）を指し、接続先 PDS のホスト名とは別概念。`atproto.Client` の PDS ホストは非公開フィールドで外部から参照できず、公開アクセサの追加は別関心事のため見送る
- **Slack Block Kit（`blocks` フィールド）への移行**: 0012 の判断を継続する。既存の legacy attachments API（`attachments[].color` + `fields`）で本タスクの要求は過不足なく満たせる
- **通知先チャンネル振り分けロジックの変更**: 0006/0012 で確定済みのロジック（`isFailure`）はそのまま使う
- **黄色（警告）の中間状態表現**: 0012 の Out of Scope を継続する

## 3. 機能要件と受け入れ基準

### F-001: 実行ホスト・bsky アカウントの識別情報の付加

Slack メッセージの attachment に、実行ホスト名と bsky アカウントの識別情報（ハンドル）を、正常系・異常系を問わず含める。ホスト名は TOML 設定ファイルのオプショナルなフィールド（`hostname`）で明示的に指定できるものとし、未指定の場合は `os.Hostname()` にフォールバックする。

**Acceptance Criteria**:
- **AC-01**: 実行が正常終了した場合・異常終了した場合のいずれも、attachment の `fields` にホスト名を示すフィールド（例: `Title: "Host"`）が含まれる
- **AC-02**: 実行が正常終了した場合・異常終了した場合のいずれも、attachment の `fields` に bsky アカウントのハンドルを示すフィールド（例: `Title: "Account"`）が含まれる
- **AC-03**: TOML 設定ファイルに `hostname` フィールドが指定されている場合、その値がそのままホスト名として使われる
- **AC-04**: TOML 設定ファイルに `hostname` フィールドが指定されていない（キー自体が無い、または空文字列）場合、`os.Hostname()` の返す値（取得に失敗した場合は AC-05 の扱い）がホスト名として使われる
- **AC-05**: `os.Hostname()` がエラーを返す場合でも、通知送信自体は失敗せず、ホスト名フィールドには空文字列またはプレースホルダが設定される（best-effort 方針により通知送信全体を止めない）
- **AC-06**: F-001 により常に非空の `fields` が存在するようになるため、正常終了時にも attachment が生成される（0012 AC-05 が定めた「完全成功時は attachment を生成しない」という規則を本タスクで変更する）

### F-002: 統計情報（対象件数・削除件数・処理時間）の付加

`runner.Run()` によるログイン・一覧取得・削除処理の実行に到達した場合に限り、削除対象件数・実削除件数・処理時間を attachment の `fields` に構造化フィールドとして含める。

**Acceptance Criteria**:
- **AC-07**: `outcome.Result != nil` の場合（削除対象の判定処理に到達した場合）、attachment の `fields` に削除対象件数（`len(Result.Targets)`）を示すフィールドが含まれる
- **AC-08**: `outcome.Result != nil` の場合、attachment の `fields` に実削除件数（`len(Result.Deleted)`）を示すフィールドが含まれる
- **AC-09**: `outcome.Result != nil` の場合、attachment の `fields` に処理時間（`runner.Run()` 呼び出し開始から終了までの経過時間）を示すフィールドが含まれる
- **AC-10**: `outcome.Result == nil` の場合（認証失敗など、削除対象の判定処理に到達する前に実行が中断した場合）、統計情報フィールド（対象件数・削除件数・処理時間）はいずれも含まれない
- **AC-11**: 処理時間の計測は `runner.Run()` の呼び出し直前から呼び出し直後までの区間のみを対象とし、設定読み込み・フラグパースに要した時間は含まない

### F-003: `text` からの件数表現の除去

`text` フィールドの一行サマリから、削除件数・失敗件数などの数値表現を除去し、成功/失敗を示す絵文字と短い状態文言のみで構成する。件数の詳細は F-002 で `fields` に構造化情報として格納されるため、`text` 側での重複表現を無くす。

**Acceptance Criteria**:
- **AC-12**: 正常終了時の `text` に、削除件数を示す数値が含まれない
- **AC-13**: 異常終了時（部分失敗・実行中断のいずれも含む）の `text` に、削除件数・失敗件数を示す数値が含まれない
- **AC-14**: `text` は引き続き、成功/失敗を示す絵文字と、実行結果を一目で判別できる短い状態文言を含む（0012 AC-01/AC-02 の絵文字判別要件を後退させない）

## 4. 非機能要件

- **NF-001**: `make fmt`・`make test`・`make lint` が成功する。
- **NF-002**: ホスト名・アカウント名・統計情報の付加ロジックについて、Webhook への実際のネットワーク通信なしに単体テストできること（0006 NF-002・0012 NF-002 と同様の方針）。
- **NF-003**: ホスト名・アカウントハンドルも既存の `sanitizeForPayload`（制御文字除去 + mrkdwn エスケープ）の対象とし、0006/0012 で確立したペイロードのサニタイズ保証を後退させない。
- **NF-004**: 秘密情報（app パスワード・セッション JWT・`Authorization` ヘッダー値・Slack Webhook URL）が新しいフィールドのいずれにも含まれない（0006 AC-19・0012 AC-11 の継続）。
- **NF-005**: 投稿本文（body）そのものが新しいフィールドのいずれにも含まれない（0006 AC-14・0012 AC-12 の継続）。
- **NF-006**: Go 1.26.2 以上でビルドできること。
- **NF-007**: 既存の `make notify-preview` 開発者ツール（`docs/dev/developer_guide/notify_preview.md`）が新しいフィールド構成でも動作し、開発者がローカルで確認できること。

## 5. スコープ外の根拠

- **PDS ホストの付加**: 本タスクの目的は「どの実行がこの通知を出したか」の運用上の識別であり、bsky-cleaner を実行する計算機のホスト名で足りる。接続先 PDS のホスト名は `atproto.Client` の非公開フィールドであり、公開アクセサの追加は本タスクの目的に対して不要な変更範囲の拡大になるため見送る。
- **Block Kit への移行**: 0012 での判断（YAGNI、legacy attachments API で要求を満たせる）を継続する。
- **通知先チャンネル振り分けロジックの変更**: 本タスクはメッセージの内容（`fields`/`text`）を変更するものであり、送信先の選択ロジック（`isFailure`）は変更しない。

## 6. 成功基準（要約）

- AC-01〜AC-14 が test/static で緑。
- `--apply` 実行時、Slack 通知の attachment に実行ホスト名・bsky アカウントのハンドルが正常系・異常系を問わず表示され、削除処理に到達した実行では削除対象件数・削除件数・処理時間も表示される。認証失敗など削除処理に到達しなかった実行では統計情報フィールドが表示されない。`text` の一行サマリから件数表現が無くなり、絵文字による正常系/異常系の判別（0012 の保証）は維持される。
