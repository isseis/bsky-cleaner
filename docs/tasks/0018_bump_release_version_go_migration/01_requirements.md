## 1. 背景と目的

### 1.1 背景

`scripts/bump-release-version.sh` は、リリース前に `docker-compose.yml` の `image:` タグと
`README.md`/`README.ja.md` の `VERSION=` 行を一括更新する Bash スクリプトである
（[docker_deployment.md](../../design/docker_deployment.md) 参照）。

このスクリプトはコードレビューを経て、以下3件の脆弱性クラスへの対処が行われた：

1. **引数インジェクション**: バージョン引数を `echo "$1" | grep` で検証すると、`grep` は行単位でマッチするため
   `$'v1.2.3\n<payload>'` のような複数行入力が「1行目はクリーンな semver」として通過し、`sed` の置換式に
   ペイロードが混入し得た。`[[ =~ ]]` による全体アンカー一致に変更することで対処済み。
2. **symlink 経由の任意ファイル書き込み**: 予測可能な `${file}.tmp` への書き込みは、攻撃者が事前に
   そのパスへ symlink を仕込んでおくことでリポジトリ外の任意ファイルを上書きされ得た。`mktemp` で
   同一ディレクトリ上にランダム化された非 symlink の一時ファイルを作成し、アトミックに `mv` することで対処済み。
3. **パーミッション劣化**: `mktemp` が作成する一時ファイルは mode `0600` であり、`mv` は移動元（一時ファイル）の
   mode を保持するため、対処しなければ `README.md`/`docker-compose.yml` 等の追跡対象ファイルが
   サイレントに `0644` から `0600` に劣化し得た。`stat` で元の mode を退避し、置換後に `chmod` で
   復元することで対処済み。

さらに、上記3件とは別に **CI（Linux ランナー）上での動作不良** が1件発見されている
（GitHub Actions run [29223152499](https://github.com/isseis/bsky-cleaner/actions/runs/29223152499/job/86732083834)、
PR #155）：

4. **BSD/GNU `stat` のフラグ名衝突による fallback の不発**: パーミッション退避のために
   `stat -f %Lp "$file" 2>/dev/null || stat -c %a "$file"` という「BSD で失敗したら GNU にフォールバック」
   という記述をしていたが、GNU `stat` は `-f` も受理してしまう（ただし意味が全く異なり、
   「ファイルではなくファイルシステムの状態を表示する」オプション）。そのため GNU `stat -f %Lp <file>` は
   **終了コード0で成功したまま、ファイルシステム情報のダンプという無関係な出力**を返し、`||` による
   フォールバックが発火しなかった。その無関係な出力がそのまま `chmod` に渡され、
   `chmod: invalid mode` で失敗し、Linux 版 CI（`make test`）が壊れた（macOS では `-f` が期待通り
   失敗するため気づかれなかった）。修正は `stat -c %a "$file" 2>/dev/null || stat -f %Lp "$file"` と
   GNU 側から先に試す順序への入れ替え（BSD `stat` は未知のオプション `-c` を確実に非ゼロ終了で
   拒否するため、この順序であれば `||` によるフォールバックが正しく機能する）。ブランチ
   `issei/readme-config-toml-example` のコミット `a6e8b7b` (`fix: correct stat -f/-c fallback order in
   bump-release-version.sh`) で対処済み。

   この事例は、他の3件（意図的な攻撃を想定したセキュリティ上の脆弱性）とは性質が異なり、
   **「移植性のための `||` フォールバックが、片方の実装が同名フラグを異なる意味で受理するために
   静かに発火しない」という、シェルスクリプト特有の正確性バグ**である。CI で偶然発見されるまで
   ローカル（macOS）開発では顕在化しなかった点が、シェルスクリプトのテスト容易性の低さを
   象徴している。

これらを受けて、Bash と Go/Python のどちらが中長期的に妥当かを多角的にレビューした結果、以下の結論に至った：

- **中期的には Go への書き換えが望ましい**: 本リポジトリは既に Go の品質ゲート（`make test`/`make lint`/
  `testify`）を持っており、そこに乗せる限界コストが低い。現状のシェル実装は防御コード（symlink 対策、
  BSD/GNU `stat` 分岐、`sed` メタ文字エスケープ）が既にシェルスクリプトとしては異例な分量に膨らんでおり、
  型付き API（`regexp`, `os.CreateTemp`, `os.Chmod` 等）に置き換えた方が将来のレビュー・変更コストが下がる。
  特に4件目の `stat` フラグ衝突は、Go であれば `os.Stat`/`os.Chmod` という単一の標準ライブラリ API で
  OS 差異ごと解消され、そもそも発生し得ないクラスの問題である。
- **Python は選択肢から除外**: 本リポジトリは Go に統一されており（`docs/dev/developer_guide` 参照、
  external-dependency-minimization の方針とも整合）、新規言語ツールチェーン（venv/uv 等、CI/Lint の二重化）を
  持ち込むコストが本タスクの規模に見合わない。
- **緊急性は低い**: 本スクリプトはリリース毎に開発者本人が手動で1回実行するのみで、CI 非経由・
  攻撃対象として限定的である。現行の Bash 実装は上記4件（脆弱性3件・CI 上の動作不良1件）に
  既に対処済みであり、現時点で実害はない。

### 1.2 目的（ゴール）

- 将来 Go 移行に着手する際に、現行 Bash 実装が保証している安全特性・CLI 契約を過不足なく引き継ぐための
  受け入れ基準を明文化しておくこと。
- 本タスクは **draft のまま当面レビュー・着手しない**（着手時期未定）。リリース手順の自動化や
  CI 組み込みを検討するタイミングで、本ドキュメントを起点に再評価する。

## 2. スコープ

### In Scope

- **F-001**: `scripts/bump-release-version.sh` と同等の機能（`docker-compose.yml` / `README.md` /
  `README.ja.md` のバージョン文字列一括更新）を Go で再実装すること。

### Out of Scope

- リリース手順そのものの自動化（`git commit`/`push`/`tag`/PR 作成の自動化） — 現行スクリプトも
  意図的にこれらを行わず、人間が確認・実行する設計になっているため、本タスクでもその方針を踏襲する。
- CI（GitHub Actions 等）への組み込み — 現時点でこのスクリプトは手動実行のみを想定しており、
  自動実行フローの設計は別タスクとする。
- 実装配置先（`cmd/` 配下のサブコマンドにするか、`scripts/` 配下に単体の Go ファイル/`go run` 対象として
  置くか）の決定 — 着手時点でのリポジトリ構成・`Package Reference` を踏まえて改めて判断する。

## 3. 機能要件と受け入れ基準

各機能要件には、独立して検証可能な受け入れ基準（Acceptance Criteria）を明示すること。
AC の採番ルールは [requirements_process.md](../../dev/developer_guide/requirements_process.md) を参照。

### F-001: バージョン文字列の一括更新

開発者がリリース前に1つの semver バージョン文字列（`vX.Y.Z`）を引数として与えると、
`docker-compose.yml` の `image:` タグと `README.md`/`README.ja.md` の `VERSION=` 行を
その値に書き換える。

**Acceptance Criteria**:
- **AC-01**: コマンドライン引数は `vX.Y.Z`（`v` + 数字.数字.数字）の形式に **文字列全体を** アンカーして
  一致するかを検証すること。部分一致や複数行を含む入力は拒否し、非ゼロ終了すること。
- **AC-02**: 各対象ファイル（`docker-compose.yml`, `README.md`, `README.ja.md`）について、置換対象のパターンが
  存在することを置換前に確認し、存在しない場合（フィールドのリネーム・行の移動・ファイル不在等）は
  エラーメッセージを出力して非ゼロ終了すること。既存の一致確認と置換に使用するパターンは同一のものを
  用い、確認範囲より広い範囲を置換しないこと。
- **AC-02a**: 置換は一致行内のバージョン文字列のみを対象とし、行頭の接頭辞（`VERSION=`、
  `image: ghcr.io/...:` 等）および**バージョン以降の行末残余（後続の空白・コメント等）を原文のまま保持する
  こと**。特に `README.md`/`README.ja.md` の `VERSION=vX.Y.Z  # ...` のような末尾コメントを破壊しないこと。
  一致行以外の行、およびファイルのその他の内容は一切変更しないこと。
- **AC-02b**: `docker-compose.yml` に併存する、コメントアウトされた digest 固定行
  （例: `# image: ghcr.io/isseis/bsky-cleaner@sha256:<digest>`）は書き換え対象とせず、原文のまま保持すること。
- **AC-03**: ファイルの書き換えは、同一ディレクトリ上に作成したランダム化された一時ファイルへ書き込んだ後、
  アトミックにリネームする方式で行うこと。一時ファイルのパスは予測可能であってはならず、
  事前に配置された symlink を追跡して書き込んでしまわないこと。
- **AC-04**: 書き換え後、対象ファイルの元のパーミッション（mode）が保持されていること
  （一時ファイル作成時の既定 mode に劣化しないこと）。
- **AC-05**: コマンドライン引数は1つのみを受け付けること。0個または2個以上の場合は使用法（Usage）を
  標準エラー出力し、非ゼロ終了すること。
- **AC-06**: 本コマンドは `docker-compose.yml`/`README.md`/`README.ja.md` の書き換え以外の副作用
  （`git commit`/`branch`/`tag`/`push` 等）を一切行わないこと。
- **AC-07**: 3ファイルのいずれかの処理中にエラー（ファイル不在、パターン不一致、書き込み権限エラー等）が
  発生した場合、後続ファイルの処理を行わずに停止すること（フェイルクローズ）。
- **AC-08**: 全対象ファイルの存在確認とパターン一致確認（AC-02）を、いずれのファイルへの書き込みよりも
  **先行して**一括で実施すること。1つでも検証に失敗した場合、どのファイルにも書き込みを行わずに
  非ゼロ終了すること（部分更新の防止）。
  - 補足: 現行 Bash 実装は compose → README.md → README.ja.md を逐次処理し、途中失敗時に先行ファイルの
    書き込みを残す（原子性はファイル単位に閉じる）。Go 版では検証を全書き込みに先行させることで、
    最頻の「パターン不一致・ファイル不在」ケースでの部分更新を構造的に排除する。ただし全ファイルの
    検証通過後、実書き込み段階でI/Oエラーが発生した場合の複数ファイル間ロールバックまでは要求しない
    （そこまでの原子性はスコープ外）。
- **AC-09**: 正常終了時、更新した各ファイルの通知と、後続のリリース手順（`git commit`/`tag`/`push`/PR 作成の
  手引き）を現行スクリプトと同趣旨で出力すること。この出力はあくまで人間向けの案内であり、コマンド自体は
  AC-06 のとおりこれらの操作を実行しないこと。

## 4. 非機能要件

必要に応じて `NF-XXX` の識別子を付け、実装計画書からの参照を可能にする。

- **NF-001**: `make fmt`・`make test`・`make lint` が成功すること。
- **NF-002**: Go 1.26.2 以上でビルドできること。
- **NF-003**: macOS・Linux の双方で同一の挙動をすること（現行 Bash 実装が BSD/GNU `stat` の差異を
  吸収している点を、Go の標準ライブラリ（`os.Stat`）で置き換えることで解消される想定）。
  現行 Bash 実装では、この差異吸収のための `||` フォールバックの順序を誤ったことで、Linux CI
  でのみ `chmod: invalid mode` エラーが発生する不具合が発生している（「1.1 背景」の4件目参照）。
  Go 版では OS ごとのコマンド分岐自体が不要になるため、この種の不具合のクラスが構造的に排除される
  ことを確認基準とする。
- **NF-004**: 外部依存パッケージの追加は最小限にとどめること（標準ライブラリ `regexp`/`os`/`os.CreateTemp`
  等で実現可能な範囲を優先し、大きな依存を持ち込まない）。

## 5. スコープ外の根拠

- **リリース手順の自動化（commit/push/tag/PR 作成）**: 現行スクリプトも意図的にここまでを行わない
  設計になっており（[docker_deployment.md](../../design/docker_deployment.md) 参照）、人間によるレビュー・
  確認を挟む安全策として維持する。本タスクは既存スクリプトの言語移行のみを対象とし、フロー自体の
  変更は別タスクとして切り出す。
- **CI 組み込み**: 現時点で本スクリプトは手動実行専用であり、CI 化には別途トリガー設計・権限設計が
  必要になるため、本タスクのスコープには含めない。

## 6. 成功基準（要約）

- AC-01〜AC-09（AC-02a/02b を含む） が test で緑になること。
- Go 版が現行 Bash 実装と同一の CLI 契約（引数形式・エラー時の終了コード・出力メッセージの趣旨）と
  安全特性（引数検証・symlink 安全性・パーミッション保持・フェイルクローズ）を満たすこと。
- 本ドキュメントは `draft` のまま維持し、着手判断（リリース自動化・CI 組み込み検討時）が下されるまで
  実装に着手しないこと。
