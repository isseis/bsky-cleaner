# Slack Notification Security Design

- Created: 2026-07-09
- Status: Draft
- Related documents: [Project overview](../overview.md), [Configuration reference](configuration.md)

## Positioning

This document describes the security measures in the Slack notification feature (`internal/notify` package). It covers defenses against the following attack vectors:

- Webhook URL leakage (via logs and error messages)
- Slack markup injection via message body (`@channel` / `@here` mention expansion)
- Log forgery and terminal manipulation via control characters
- Unbounded payload size growth
- Webhook transmission to malicious hosts (SSRF-like risk)

## Scope

- Webhook URL validation and redaction in the `internal/config` package
- Payload construction and transmission in the `internal/notify` package
- Retry log masking by the `internal/notify` package using the log URL masking mechanism of `internal/retry`

The following topics are out of scope for this document:

- The notification specification itself (success/failure routing etc.): see [Project overview](../overview.md#execution-result-notification)
- How to obtain Slack Incoming Webhooks and Slack app configuration procedures

## Design

### Webhook URL Redaction

A Slack Webhook URL is a value that, if known, allows anyone to post to the corresponding channel. Therefore, it is treated as sensitive information, similar to an app password.

#### Wrapping with the SecretString Type

The `SecretString` type in the `internal/config` package wraps the Webhook URL. This provides the following characteristics:

- **Protection when logging**: When formatted with `%v`/`%s`/`%#v` or through structured logging via `log/slog`, it is replaced with the fixed string `[REDACTED]`.
- **Value retrieval**: The actual value can only be retrieved by calling `Reveal()`. It is designed to be called only immediately before constructing the HTTP request for the Slack notification payload.

The `SecretString` implementation is in `internal/config/secret.go` and implements the `fmt.Stringer`, `fmt.GoStringer`, and `slog.LogValuer` interfaces.

#### Webhook URL Log Masking

The `redactWebhookURL` function in the `internal/notify` package masks the URL output in retry logs from the `internal/retry` package. Only the scheme and host are recorded in the logs; the path (including the Webhook token) is replaced with `[REDACTED]`.

```go
func redactWebhookURL(req *http.Request) string {
    return fmt.Sprintf("%s://%s/[REDACTED]", req.URL.Scheme, req.URL.Host)
}
```

### Webhook URL Host Validation

The `slack_allowed_host` field in the TOML configuration file specifies the allowed host (e.g., `hooks.slack.com`), and the host portion of the configured Webhook URL is validated against it. Validation is performed by the `validateSlackAllowedHost` function in `internal/config/validate.go`.

- For both success and failure Webhook URLs, verify that the host portion (excluding port number, case-insensitive) matches `slack_allowed_host`.
- If they do not match, the system is fail-closed. That is, rather than giving up on sending the notification upon a validation error, the tool itself fails to start as a configuration error.
- If both Webhook URLs are unset (environment variables are empty), the tool does not fail to start even if `slack_allowed_host` is unset.
- If any Webhook URL is set, `slack_allowed_host` is required.

### Payload Sanitization

The `sanitizeForPayload` function in `internal/notify/payload.go` applies two-stage sanitization to externally sourced text included in the Slack notification payload.

#### Stage 1: Control Character Removal

The `Sanitize` function in `internal/notify/sanitize.go` (which delegates to `internal/sanitize.ControlChars`) removes C0 control characters (0x00-0x1F, including ESC 0x1B) and DEL (0x7F).

- **ANSI escape sequence countermeasure**: By removing ESC (0x1B), ANSI escape injection that manipulates terminal emulator screens or clipboard writes is prevented.
- **Log injection countermeasure**: Newlines (`\n`, `\r`) are also removed as C0 control characters, preventing destruction of Slack message structure and log forgery.

#### Stage 2: Slack Markup Escaping

The `escapeSlackMarkup` function neutralizes Slack's mrkdwn special notation. In particular, it prevents the following patterns:

- Mention syntax such as `<!channel>` / `<!here>` / `<!subteam^ID>` (starting with `<`)
- Other markup syntax

The escape order is as follows:

1. The ampersand (`&`) is escaped to `&amp;` first (done first to prevent re-escaping of the `&` sequence generated by subsequent escapes)
2. The less-than sign (`<`) is then escaped to `&lt;`
3. The greater-than sign (`>`) is then escaped to `&gt;`

#### Restriction of Information Included in the Payload

The Slack notification payload includes only the following information, and does not include any message body:

- Execution result type (success/failure)
- Deletion count and failure count
- rkey of posts that failed to delete
- Error type (classification text by `errorKind`)

`atproto.Post` is designed without a message body field, and there is no code path where a message body is included in the payload.

### Payload Size Limit

The `buildPayload` function limits the output text to `maxPayloadLength` (4,000 bytes). When exceeded, the end is truncated and `...(truncated)` is appended. This prevents unbounded payload growth even when a large number of deletion failures occur.

### Sensitive Information Protection in Error Messages

The `SendError` type in `internal/notify/notify.go` does not include the following in the error message for Webhook transmission errors:

- The Webhook URL itself
- Raw `net/http` / `net/url` error strings

The `Error()` method returns only the error type (classification by `errorKind`) or the HTTP status code.

```go
func (e *SendError) Error() string {
    if e.StatusCode == 0 {
        return fmt.Sprintf("slack notify: send failed: %s", errorKind(e.Err))
    }
    return fmt.Sprintf("slack notify: send failed: HTTP status %d", e.StatusCode)
}
```

### Retry and Timeout

#### Retry Policy

The retry policy for Slack notifications is intentionally lighter than the retry for API calls (`internal/atproto`). The reason is that Slack notification failures do not affect the CLI exit code (non-fatal), and priority is given to keeping the worst-case delay short.

- Maximum retry count: 2
- Initial backoff: 1 second
- Maximum backoff: 4 seconds

#### Per-Attempt Timeout

`perAttemptTimeoutDoer` applies an independent timeout (default 3 seconds) to each retry attempt. This prevents a single slow attempt from consuming the budget of subsequent attempts. Since the `Doer` in `internal/retry` clones and reuses the same request (and its context) for all attempts, without this wrapper, a timeout on the first attempt would immediately cancel subsequent attempts.

## Attack Vector and Countermeasure Mapping Table

| Attack Vector | Countermeasure | Implementation Location |
|---|---|---|
| Webhook URL leakage in logs | Masking with `SecretString` type | `internal/config/secret.go` |
| Webhook URL leakage in logs (retry logs) | URL masking with `redactWebhookURL` | `internal/notify/notify.go` |
| Webhook transmission to malicious hosts | Host validation with `slack_allowed_host` (fail-closed) | `internal/config/validate.go` |
| Slack mention injection (`@channel`, etc.) | Escaping of `<`/`>`/`&` with `escapeSlackMarkup` | `internal/notify/payload.go` |
| ANSI escape injection | Removal of ESC (0x1B) with `Sanitize` | `internal/notify/sanitize.go` |
| Log injection (newline insertion) | Newline removal with `Sanitize` | `internal/notify/sanitize.go` |
| Payload bloat | Limiting with `maxPayloadLength` (4,000 bytes) | `internal/notify/payload.go` |
| Sensitive information leakage via error messages | Exclusion of URL and raw error strings in `SendError.Error()` | `internal/notify/notify.go` |
| Hanging during transmission | Per-attempt timeout with `perAttemptTimeoutDoer` | `internal/notify/notify.go` |
