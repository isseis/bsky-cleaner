# Security Design

- Created: 2026-07-02
- Status: Draft
- Related Documents: [Project Overview](../overview.md)

## Position

This document describes the implementation-level details of the risk categories listed in the "Security Considerations" section of the [Project Overview](../overview.md). For policy-level decisions, refer to the overview; this document only addresses "how to handle them."

## Attack Vectors to Consider

Although the Bluesky official API is used, the AT Protocol is a federated structure where the actual communication partner is each user's PDS determined by DID resolution, not necessarily `bsky.social` itself. Therefore, attack vectors that assume the communication destination is broken or under the control of an attacker (malicious PDS, compromised PDS, DID document spoofing, etc.) must also be considered, and it cannot be said that "because it is the official API, typical DoS is unlikely." Safety-related policies are also described in other sections (see [Safety Policy](../overview.md#safety-policy), [Retry Policy](../overview.md#retry-policy), [Information Leakage Protection in Slack Notifications](../overview.md#information-leakage-protection-in-slack-notifications)), and this document supplements the attack vectors not covered by those sections.

- **Indirect injection via post body**: If the post body (which may include content from reply targets or quoted sources, even for your own posts) is included as-is in Slack notifications or console output, it may cause unintended notification diffusion via `@channel` / `@here` mentions, ANSI escape sequence injection (screen manipulation, clipboard writing, etc.), or log forgery via log line breaks (log injection).
- **Risks arising from the AT Protocol's federated structure**: Actual data is not necessarily stored on `bsky.social` but on each user's PDS determined by DID resolution. If there is a flaw in the DID resolution or PDS endpoint determination logic, app passwords or session tokens may be sent to unintended hosts (effectively an SSRF).
- **Resource exhaustion (DoS) from a broken or attacker-controlled PDS**: Even if the PDS pointed to by DID resolution is broken or under the control of an attacker, after passing through legitimate SSRF countermeasures (communicating only with allowed destinations), the response content itself can become an attack vector. The following measures currently mitigate all types of this kind of attack.
  - **Countermeasure against memory exhaustion from large response bodies**: The DID resolution path (`internal/atproto/did.go`) imposes `io.LimitReader` limits on response size (8 KiB for handle resolution, 64 KiB for DID documents). The common XRPC call path (`doXRPC` in `internal/atproto/http.go`) used by login, post listing, and deletion also reads with `io.LimitReader` capped at `maxXRPCResponseBytes` (8 MiB), treating excess as a `ResponseTooLarge` error.
  - **Countermeasure against resource exhaustion from endless pagination**: `listAllRecords` (`internal/atproto/posts.go`) stops when the cursor equals the previous response value (`ErrPaginationStalled`), and also imposes limits of `maxListPages` (10,000 pages), `maxListRecords` (1,000,000 records), and `maxListTotalBytes` (256 MiB). Even if an attacker evades `ErrPaginationStalled` detection by returning different cursor values each time, processing is aborted when any of these limits is reached.
  - **Countermeasure against hanging from response delay (slowloris-like behavior)**: The `http.Client` used for XRPC calls sets a connection establishment timeout (`dialTimeout`, 10 seconds) as well as `xrpcRequestTimeout` (30 seconds) as the timeout for the entire request (including connection, sending, and response reading). This ensures that a single XRPC call does not hang indefinitely against a server that continuously sends extremely slow responses. In addition, [0005_retry_timeout](../tasks/0005_retry_timeout/01_requirements.md) F-002 and NF-003 specify that the execution timeout deadline is propagated to the `context.Context` of individual XRPC calls (including login, post listing, and deletion), providing double protection against hanging via both the per-request limit and the remaining budget of the execution timeout. For deletion calls, AC-08 individually stipulates that forced interruption upon reaching this propagated deadline is permitted.
- **Sensitive information leakage via error messages and stack traces**: Cases where an object containing the `Authorization` header or session JWT is wrapped as-is in an HTTP client error and leaks to panic logs or Slack error notifications. Masking via text pattern matching alone may allow code that outputs structs directly to pass through.
- **Self-inflicted access rate limiting from retries and cron**: Without an upper bound on exponential backoff, continuous errors may cause repeated hitting that triggers Bluesky-side rate limiting or account restrictions.
- **Resource exhaustion from multiple concurrent executions**: If the next cron invocation occurs while deletion processing is still in progress, multiple processes may run simultaneously, leading to memory pressure (swap occurrence, etc.) or affecting other processes on the host. As a countermeasure, a timeout is set on execution time, configured to be sufficiently shorter than the schedule interval to prevent concurrent execution (exclusive control such as lock files is not adopted in favor of implementation simplicity).
- **Configuration file tampering and permissions**: If there is local access to the TOML configuration or application execution environment, tampering with `retention_days` could cause "immediate deletion of all posts." Candidate countermeasures include configuration file permission management and tamper detection.
- **Idempotency of deletion processing**: If a target post has already been deleted between fetching the post list and executing the deletion, it should be handled as a normal case without crashing. Also, as per [0005_retry_timeout](../tasks/0005_retry_timeout/01_requirements.md) AC-08/AC-09, the execution timeout may forcibly interrupt even during a deletion API call, in which case the post is treated as incomplete (unable to confirm success or failure) rather than "deletion completed." The safety of this treatment relies on the idempotency of `DeleteRecord` ([0002_atproto_client](../tasks/0002_atproto_client/01_requirements.md) AC-12), and it is safe to retry deletion of the same post on the next execution.
- **Docker image supply chain risks**: Referencing a base image by tag (e.g., `latest`) may change its contents with each build. Base images should be pinned by digest (e.g., `alpine@sha256:...`) to prevent unintended changes from being introduced.
