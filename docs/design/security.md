## 位置付け

本ドキュメントは、[プロジェクト概要](../overview.md) の「セキュリティ考慮事項」で挙げたリスクカテゴリの実装レベルの詳細を記載する。方針レベルの決定事項は overview 側を参照し、ここでは「どう対処するか」のみを扱う。

## 考慮すべき攻撃ベクトル

Bluesky 公式 API を利用するが、AT Protocol はフェデレーション構造上、実際の通信相手は DID 解決の結果決まる各ユーザーの PDS であり、`bsky.social` そのものとは限らない。したがって通信先が壊れている、あるいは攻撃者の管理下に落ちているケース（悪意ある PDS・侵害された PDS・DID ドキュメントの偽装等）を前提にした攻撃ベクトルも考慮が必要であり、「公式 API だから典型的な DoS は想定しにくい」とは言えない。安全性に関する方針は他のセクション（[安全性についての方針](../overview.md#安全性についての方針)、[リトライ方針](../overview.md#リトライ方針)、[Slack 通知における情報漏洩対策](../overview.md#slack-通知における情報漏洩対策)）にも記載しており、本ドキュメントはそれらで扱っていない攻撃ベクトルを補足するものである。

- **投稿本文経由の間接的なインジェクション**: 投稿本文（自分の投稿だが、リプライ相手・引用元の内容を含みうる）を Slack 通知やコンソール出力にそのまま含めると、`@channel` / `@here` メンションによる意図しない通知拡散、ANSI エスケープシーケンス注入（画面操作・クリップボード書き込み等）、ログ改行混入によるログ偽装（log injection）が起こりうる
- **AT Protocol のフェデレーション構造に起因するリスク**: 実データは `bsky.social` とは限らず DID 解決で決まる各ユーザーの PDS に置かれる。DID 解決や PDS エンドポイント決定ロジックに不備があると、app パスワードやセッショントークンを意図しないホストへ送ってしまう可能性がある（実質的な SSRF）
- **壊れた・攻撃者管理下の PDS によるリソース枯渇（DoS）**: DID 解決が指す先の PDS そのものが壊れている、または攻撃者の管理下にある場合、正規の SSRF 対策（許可された宛先のみに通信する）を通過した後でも、その応答内容自体が攻撃手段になりうる。DID 解決経路（`internal/atproto/did.go`）は応答サイズに `io.LimitReader` の上限を設けているが、ログイン・投稿一覧取得・削除が使う XRPC 呼び出しの共通経路（`internal/atproto/http.go` の `doXRPC`）にはレスポンスサイズの上限がなく、同様の防御が抜けている。具体的には次のような攻撃が成立しうる。
  - **巨大なレスポンスボディによるメモリ枯渇**: `doXRPC` は `json.NewDecoder(resp.Body).Decode(out)` でレスポンスボディを無制限に読み込む。攻撃者は `listRecords`/`getRecord` に対して巨大な JSON（肥大化した `value` フィールド、大量の `records` 配列等）を返すことで、プロセスの OOM を誘発できる
  - **終わらないページネーションによるリソース枯渇**: `listAllRecords`（`internal/atproto/posts.go`）はカーソルが直前の応答と同一値になった場合のみ停止する（`ErrPaginationStalled`）。攻撃者が毎回異なるカーソル値を返し続ければこの検知をすり抜け、総ページ数・総レコード数の上限がないため、リクエストとメモリ使用量が際限なく積み上がる
  - **応答遅延（slowloris 的挙動）によるハング**: XRPC 呼び出しに使う `http.Client` は接続確立のタイムアウト（`dialTimeout`）のみを設定しており、リクエスト全体のタイムアウト（`http.Client.Timeout`）を設定していない。極端に低速な応答を送り続けるサーバーに対し、呼び出しが無期限にハングしうる
- **エラーメッセージ・スタックトレース経由の秘密情報漏洩**: HTTP クライアントのエラーに `Authorization` ヘッダーやセッション JWT を含むオブジェクトがそのままラップされ、panic ログや Slack エラー通知に流出するケース。テキストパターンマッチによるマスキングだけでは、構造体をそのまま出力するようなコードは素通りしうる
- **リトライ・cron 起因の自滅的なアクセス制限**: 指数バックオフの上限を設けないと、継続的なエラー時に叩き続けて Bluesky 側のレート制限やアカウント制限を誘発しうる
- **多重起動によるリソース枯渇**: 削除処理に時間がかかっている最中に cron の次回起動が発生すると、複数プロセスが同時に実行され、メモリ圧迫（スワップ発生等）やホストの他プロセスへの影響を招きうる。対策として実行時間にタイムアウトを設け、スケジュール間隔より十分短く設定することで多重起動を防ぐ（ロックファイル等の排他制御は、実装の単純さを優先し採用しない）
- **設定ファイルの改ざん・権限**: TOML やアプリ実行環境へのローカルアクセスがある場合、`retention_days` の改ざんで「全投稿即削除」を引き起こせる。設定ファイルの権限管理・改ざん検知が対策候補となる
- **削除処理の冪等性**: 投稿一覧取得後、削除実行までの間に対象投稿が既に削除されていた場合でも、クラッシュせず正常系として扱えるようにする。また、タイムアウトによる強制終了は 1 件の削除 API 呼び出しの途中ではなく、投稿単位の処理境界で効かせる（呼び出し完了後に次の投稿へ進む前にタイムアウトを確認する）ことで、削除が成功したか不明な中途半端な状態を避ける
- **Docker イメージのサプライチェーンリスク**: ベースイメージをタグ（例: `latest`）で参照すると、ビルドごとに内容が変わりうる。ベースイメージは digest（例: `alpine@sha256:...`）で固定し、意図しない変更の混入を防ぐ
