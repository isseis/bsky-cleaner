# セキュリティ設計

- 作成日: 2026-07-02

- 関連ドキュメント: [プロジェクト概要](../overview.ja.md)

## 位置付け

本ドキュメントは、[プロジェクト概要](../overview.ja.md) の「セキュリティ考慮事項」で挙げたリスクカテゴリの実装レベルの詳細を記載する。方針レベルの決定事項は overview 側を参照し、ここでは「どう対処するか」のみを扱う。

## 考慮すべき攻撃ベクトル

Bluesky 公式 API を利用するが、AT Protocol はフェデレーション構造上、実際の通信相手は DID 解決の結果決まる各ユーザーの PDS であり、`bsky.social` そのものとは限らない。したがって通信先が壊れている、あるいは攻撃者の管理下に落ちているケース（悪意ある PDS・侵害された PDS・DID ドキュメントの偽装等）を前提にした攻撃ベクトルも考慮が必要であり、「公式 API だから典型的な DoS は想定しにくい」とは言えない。安全性に関する方針は他のセクション（[安全性についての方針](../overview.ja.md#安全性についての方針)、[リトライ方針](../overview.ja.md#リトライ方針)、[Slack 通知における情報漏洩対策](../overview.ja.md#slack-通知における情報漏洩対策)）にも記載しており、本ドキュメントはそれらで扱っていない攻撃ベクトルを補足するものである。

- **投稿本文経由の間接的なインジェクション**: 投稿本文（自分の投稿だが、リプライ相手・引用元の内容を含みうる）を Slack 通知やコンソール出力にそのまま含めると、`@channel` / `@here` メンションによる意図しない通知拡散、ANSI エスケープシーケンス注入（画面操作・クリップボード書き込み等）、ログ改行混入によるログ偽装（log injection）が起こりうる
- **AT Protocol のフェデレーション構造に起因するリスク**: 実データは `bsky.social` とは限らず DID 解決で決まる各ユーザーの PDS に置かれる。DID 解決や PDS エンドポイント決定ロジックに不備があると、app パスワードやセッショントークンを意図しないホストへ送ってしまう可能性がある（実質的な SSRF）
- **壊れた・攻撃者管理下の PDS によるリソース枯渇（DoS）**: DID 解決が指す先の PDS そのものが壊れている、または攻撃者の管理下にある場合、正規の SSRF 対策（許可された宛先のみに通信する）を通過した後でも、その応答内容自体が攻撃手段になりうる。以下の対策により、この種の攻撃は現状すべて緩和されている。
  - **巨大なレスポンスボディによるメモリ枯渇への対策**: DID 解決経路（`internal/atproto/did.go`）は応答サイズに `io.LimitReader` の上限（ハンドル解決 8 KiB、DID ドキュメント 64 KiB）を設けている。ログイン・投稿一覧取得・削除が使う XRPC 呼び出しの共通経路（`internal/atproto/http.go` の `doXRPC`）も、`maxXRPCResponseBytes`（8 MiB）を上限に `io.LimitReader` で読み込み、超過時は `ResponseTooLarge` エラーとして扱う
  - **終わらないページネーションによるリソース枯渇への対策**: `listAllRecords`（`internal/atproto/posts.go`）は、カーソルが直前の応答と同一値になった場合に停止する（`ErrPaginationStalled`）ことに加え、`maxListPages`（10,000 ページ）・`maxListRecords`（1,000,000 件）・`maxListTotalBytes`（256 MiB）の上限を設けている。攻撃者が毎回異なるカーソル値を返し続けて `ErrPaginationStalled` の検知をすり抜けても、これらの上限のいずれかに達した時点で処理を打ち切る
  - **応答遅延（slowloris 的挙動）によるハングへの対策**: XRPC 呼び出しに使う `http.Client` は、接続確立のタイムアウト（`dialTimeout`、10秒）に加え、`xrpcRequestTimeout`（30秒）をリクエスト全体（接続・送信・応答読み込みを含む）のタイムアウトとして設定している。これにより、単一の XRPC 呼び出しは極端に低速な応答を送り続けるサーバーに対しても無期限にはハングしない。加えて [0005_retry_timeout](../tasks/0005_retry_timeout/01_requirements.md) の F-002・NF-003 が実行タイムアウトの deadline を個々の XRPC 呼び出し（ログイン・投稿一覧取得・削除を含む）の `context.Context` に伝播させる設計としているため、リクエスト単独の上限と実行タイムアウトの残り予算の両方で二重にハングを防いでいる。削除呼び出しについては、この伝播した deadline への到達時に強制中断してよいことが AC-08 で個別に規定されている
- **エラーメッセージ・スタックトレース経由の秘密情報漏洩**: HTTP クライアントのエラーに `Authorization` ヘッダーやセッション JWT を含むオブジェクトがそのままラップされ、panic ログや Slack エラー通知に流出するケース。テキストパターンマッチによるマスキングだけでは、構造体をそのまま出力するようなコードは素通りしうる
- **リトライ・cron 起因の自滅的なアクセス制限**: 指数バックオフの上限を設けないと、継続的なエラー時に叩き続けて Bluesky 側のレート制限やアカウント制限を誘発しうる
- **多重起動によるリソース枯渇**: 削除処理に時間がかかっている最中に cron の次回起動が発生すると、複数プロセスが同時に実行され、メモリ圧迫（スワップ発生等）やホストの他プロセスへの影響を招きうる。対策として実行時間にタイムアウトを設け、スケジュール間隔より十分短く設定することで多重起動を防ぐ（ロックファイル等の排他制御は、実装の単純さを優先し採用しない）
- **設定ファイルの改ざん・権限**: TOML やアプリ実行環境へのローカルアクセスがある場合、`retention_days` の改ざんで「全投稿即削除」を引き起こせる。設定ファイルの権限管理・改ざん検知が対策候補となる
- **削除処理の冪等性**: 投稿一覧取得後、削除実行までの間に対象投稿が既に削除されていた場合でも、クラッシュせず正常系として扱えるようにする。また、[0005_retry_timeout](../tasks/0005_retry_timeout/01_requirements.md) AC-08/AC-09 の通り、実行タイムアウトは削除 API 呼び出しの途中でも強制中断してよく、その場合は当該投稿を「削除完了」ではなく削除の成否が確認できない未完了として扱う。この扱いの安全性は `DeleteRecord` の冪等性（[0002_atproto_client](../tasks/0002_atproto_client/01_requirements.md) AC-12）に依拠しており、次回実行時に同じ投稿への削除を再試行しても安全である
- **Docker イメージのサプライチェーンリスク**: ベースイメージをタグ（例: `latest`）で参照すると、ビルドごとに内容が変わりうる。ベースイメージは digest（例: `alpine@sha256:...`）で固定し、意図しない変更の混入を防ぐ
